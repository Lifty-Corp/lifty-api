# HubSpot grant policy ownership

`hubspot-grant-policy.ts` owns persisted grant parsing, supported scope sets,
refresh timing, refresh response validation, portal verification and safe failure
outcomes. `hubspot-grant-policy-cases.ts` is the common behavioral test matrix.
Both files contain no runtime-specific imports. The cases use only a type import.
Their canonical home is this API repository; never edit a generated consumer.

From this checkout, update or check the API's own generated copy with:

```sh
npm run policy:sync
npm run policy:check
npm run test:policy
```

These commands work without Compass or sibling repositories. `npm run verify`
runs the canonical checks as well as the API's runtime tests, typecheck and build.
Canonical Node tests use the `.node-test.mjs` suffix because the API runtime
suite is discovered separately by Vitest.

To distribute a policy change, explicitly select the participating isolated
checkouts; omitted external consumers are never read or written:

```sh
node scripts/sync-hubspot-grant-policy.mjs --jobs /path/to/jobs-worktree --db /path/to/functions-worktree --services /path/to/services-worktree
node scripts/sync-hubspot-grant-policy.mjs --check --jobs /path/to/jobs-worktree --db /path/to/functions-worktree --services /path/to/services-worktree
```

The API destination defaults to this checkout and can be selected with `--api`.
Relative arguments resolve from the caller's current directory; the canonical
source always resolves from this script's API checkout. `--check` only reads and
fails for a missing file, changed policy/cases, or changed manifest.

Each repository runs the same matrix and verifies local SHA-256 hashes against
its manifest. The selected-consumer check also compares every generated byte to
the canonical source. Updates require source, generated files and manifests
together, linked through one Linear deliverable. Record the reviewed API source
commit and all consumer commits there. Consumers
compile/deploy entirely from their own repository; no public package or sibling
checkout is required at runtime or during builds.

The initial ownership move preserves the policy and case bytes from Compass
commit `fdb1be99ffa3ea86d1d5dbebd3b721d4f6ebcb8f`; its Git history retains earlier
changes. Future policy edits belong here. Release compatibility and actual
deployments remain the responsibility of each consumer's pipeline.

## Runtime adapter contract

`resolveHubSpotGrant(options, storage)` takes an authorized workspace secret,
workspace/request IDs, injected clock and fetch, and optional `expectedPortalId`.
New callers must pass the independently resolved active integration portal.
Fresh OAuth bundles must match that portal; legacy tokens are verified against
HubSpot account details when the portal is supplied. Existing legacy runtime
callers retain pass-through behavior when they have no independent portal state.
Malformed/serialized values never pass through as bearer credentials.

Only the runtime adapter may retrieve raw secrets. It is responsible for
authorization, audit, selected workspace/integration binding and request deadline.
It supplies `rotateGrant` and `markReconnectRequired`. Rotation receives both the
previous and new grants; the API adapter also captures its database-issued
integration ID and credential version to enforce compare-and-swap in SQL.
Returning `false` or throwing from rotation produces `rotation_failed` and never
returns the new access token. Refresh failures attempt a bounded reconnect write;
the result remains credential-free even if that write throws.

The policy does not broaden scopes on refresh or introduce provider credential
proxies. Seven-scope grants remain supported until reconnect obtains the expanded
scope set. Node and Deno preserve their existing public token result interfaces.
